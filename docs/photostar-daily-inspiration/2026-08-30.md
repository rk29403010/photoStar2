# PhotoStar2 Daily Inspiration — 30 August 2026 — Preservation Health

## Repo signal

`main` still has no application-code commits after 8 August. The only later `main` change is the 26 August documentation commit that established this daily inspiration log.

The current schema already stores `file_hash`, `file_size`, dimensions and several quality fields on assets, but there is no obvious preservation/fixity workflow using those fields. That creates a useful gap between organising/restoring the archive and proving that originals are still safe.

## ★ Best next idea — Preservation Health

PhotoStar should answer a different question from ordinary photo managers:

> **What in this archive is at risk, and what should I rescue next?**

Not just backup status. A practical preservation dashboard could distinguish:

- originals with only one known copy;
- files whose hash has changed unexpectedly;
- unreadable or malformed files;
- obsolete/fragile formats;
- low-resolution or heavily compressed scans where a physical original may still exist;
- scans with clipping, blur or insufficient resolution worth redoing;
- files whose only surviving copy is on removable/cloud-only storage;
- derivatives that exist but whose true source/original cannot be located.

This fits PhotoStar particularly well because it already has hashes, quality metadata and non-destructive derivative lineage. The missing part is turning those facts into preservation decisions.

**Effort:** Medium. **Value:** Very high for a long-lived family archive.

## Current product signal

Mylio explicitly uses full-resolution Vaults and multiple devices to create redundant copies of the complete library, while showing which material is protected. Oriva, an early-access local-first archive tool, goes further by reporting one-copy-only files, duplicate groups and backup status and deliberately locking cleanup until backup has been verified. FolioSort now advertises checksum-verified moves, while Obscura Flow is explicitly aimed at verifiable archival storage with SHA-256 manifests, signatures and periodic fixity audits.

Useful references:

- Mylio automatic backup: https://mylio.com/features/auto-photo-backup/
- Mylio Vaults: https://support.mylio.com/what-is-a-vault-in-mylio-photos
- Oriva: https://oriva.xenthos.io/
- Obscura Flow: https://obscuraflow.app/photo-archive

The product gap for PhotoStar is that preservation status can be combined with family-history value. A technically weak 1950s scan of a unique person may deserve attention before a pristine 2020 JPEG, even if both are equally backed up.

## Rescue Queue

Instead of a generic quality score, PhotoStar could create a small actionable queue:

> **Worth rescanning — high priority**  
> Only known image of this person before 1960. Current scan: 640 × 480 JPEG, strong clipping, physical print known to exist.

> **Protect now**  
> 218 originals currently have only one verified copy.

> **Check source**  
> This restored image has no currently available source original.

> **Probably safe**  
> Original hash verified on two independent storage locations.

The important UX principle is to rank by **risk × historical value × ease of rescue**, not by image-quality score alone.

**Effort:** Low-medium once the preservation facts are available.

## Use professional preservation practice without turning PhotoStar into an archive server

The NDSA Levels of Digital Preservation v2.1, released in March 2026, still treats storage redundancy, integrity/fixity, metadata and content management as separate preservation concerns. It also explicitly notes that the highest level is not automatically the right target for every collection.

- NDSA Levels: https://www.ndsa.org/publications/levels-of-digital-preservation/

The Oxford Common File Layout (OCFL) is another useful design reference. It uses content digests, inventories and immutable versions so an archive remains understandable and verifiable without depending on one application.

- OCFL: https://ocfl.io/

I would **not** implement OCFL wholesale inside PhotoStar. The useful design lesson is simpler:

> a family archive should be reconstructable from ordinary files plus transparent manifests, even if PhotoStar disappears.

That suggests a future `Archive Health` export containing hashes, file identities, relationships and key metadata in straightforward JSON/CSV/Markdown alongside the originals.

## Format health — use existing preservation tooling

The open-source **Siegfried** tool identifies file formats from byte signatures using sources including The National Archives' PRONOM registry. Version 1.11.6 was released in July 2026 and includes a Windows binary plus JSON output.

Official code: https://github.com/richardlehane/siegfried

There is also a browser/WASM demonstration through Demystify Lite:

Demo: https://ross-spencer.github.io/demystify-lite/

That makes it a strong candidate for a cheap benchmark. PhotoStar could detect cases such as:

> extension says `.jpg`, actual file is TIFF

or flag formats that deserve migration/extra copies.

For deeper validation, JHOVE remains a maintained Open Preservation Foundation tool for format validation/characterisation, including JPEG and TIFF.

- JHOVE: https://openpreservation.org/products/jhove/

No new AI is required for this layer.

## AI should help decide whether a scan is worth redoing

The interesting AI use is not "is this photo pretty?" but:

> **Does this file contain as much useful visual information as its pixel dimensions imply?**

Sony's ICCV 2025 **Image Intrinsic Scale Assessment (IISA)** research estimates the largest display scale at which an image retains its best perceived quality. That is unusually relevant to old scans: a nominal 4000 px image may contain much less real detail because it was enlarged from a poor source.

Official code, dataset and pretrained inference: https://github.com/SonyResearch/IISA

Official paper/project material: https://iccv.thecvf.com/virtual/2025/poster/1850

I found no author-hosted upload-and-test demo, but the repository supports pretrained inference through Torch Hub.

For broader benchmarking, **IQA-PyTorch** exposes many no-reference and full-reference quality models including TOPIQ, MUSIQ, MANIQA and BRISQUE through one maintained toolbox.

Official toolbox: https://github.com/chaofengc/IQA-PyTorch

I would not trust any one score as a preservation decision. The Model Lab should test whether these metrics actually correlate with human judgments such as:

- worth rescanning;
- adequate for face recognition;
- adequate for OCR;
- adequate for restoration;
- adequate for normal viewing.

## New distinction — visual quality versus evidential adequacy

PhotoStar already has technical, lighting, composition and emotional quality fields. Preservation needs another concept:

**Evidential adequacy**

Examples:

- ugly but high-resolution scan of a unique 1890 portrait → **high evidence value**;
- beautiful 800 px social-media copy when a TIFF exists elsewhere → **low preservation value**;
- badly faded original scan → poor viewing quality but extremely important source evidence;
- restored face → visually strong but not a substitute for the damaged original.

That avoids a dangerous mistake: using aesthetic or restoration quality to decide what deserves preservation.

## Creative concept — The Archive Survival Test

Add a deliberately unsettling but useful button:

> **Could this archive survive without PhotoStar?**

It temporarily ignores the application database and tests what could be reconstructed from the files and exported manifests alone.

The result might say:

> **93% reconstructable**
>
> ✓ all originals located  
> ✓ hashes recorded  
> ✓ people/dated-photo relationships exported  
> ⚠ 712 captions exist only in the database  
> ⚠ 84 edit recipes have no portable sidecar  
> ⚠ 219 originals have only one verified copy

That is both a preservation feature and a powerful architectural discipline.

It would continuously pressure PhotoStar towards portable metadata, transparent lineage and low lock-in.

**Effort:** Medium eventually; a first report could be low effort.

## Best next experiment

Do not build a backup system.

Take a representative 1,000 assets and generate a read-only **Preservation Report** from facts PhotoStar already knows or can cheaply calculate:

1. original path exists;
2. current hash matches stored hash;
3. file size/dimensions;
4. number of known copies;
5. source/derivative lineage;
6. format identification;
7. crude scan-quality/resolution flags.

Then produce only three human-facing buckets:

**Protect now · Worth rescanning · Looks safe**

If that report immediately surfaces things you would actually act on, make `Preservation Health` a first-class PhotoStar concept.

The larger idea is simple:

> **A family archive is not truly organised if PhotoStar cannot tell you which memories are one disk failure, one corrupt file or one bad scan away from being lost.**
