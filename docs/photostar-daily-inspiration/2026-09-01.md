# PhotoStar2 Daily Inspiration — 1 September 2026 — Home Movie Threads

## Repo signal

`main` still has no application-code commits after 8 August 2026; the later 26 August commit only established the durable inspiration log. A repository-wide search for `video` currently returns no implementation hits, so home-movie support remains a genuine gap rather than an unfinished subsystem.

## Best next idea — Home Movie Threads

Treat home movies as a searchable extension of the still-photo archive, not a separate media silo.

The useful user actions are not generic video editing. They are family-history retrieval:

- open a still photograph and ask PhotoStar to find matching moments in home movies;
- search `Dad carrying black dog in garden` and return the exact 14-second clip rather than a whole 90-minute tape;
- find every video moment containing a known person, place or object;
- link a still photograph and a movie moment into the same event or Memory Bundle;
- extract a clean representative frame only when it adds evidence missing from the still archive.

The first product unit should therefore be a timestamped `VideoMoment`, not a whole video file.

**Effort:** Medium for a useful first version. **Value:** Very high if the archive contains legacy home movies.

## Research/code — WISE is the strongest architectural reference

The University of Oxford VGG group's 2026 **WISE** system is unusually close to the problem PhotoStar will eventually have. It is an open-source multimodal search engine spanning images, video and audio. It supports natural-language and reverse-image queries, scene/object search, face search, speech search and metadata filters, and is designed for local deployment over large collections.

Official code: https://gitlab.com/vgg/wise/wise

Paper: https://arxiv.org/abs/2602.12819

I found the official codebase, but no simple author-hosted public upload-and-test demo.

The useful lesson is architectural rather than "integrate WISE wholesale": **use one retrieval layer across stills and timed media**, so `Mum + kitchen + Christmas` can return both photographs and exact video moments.

## Research/code — Lighthouse for exact moment retrieval

LINE's open-source **Lighthouse** library is specifically designed for video moment retrieval and highlight detection. It exposes a CPU/GPU inference API, pretrained models, and an official Gradio demo that accepts a video plus a natural-language query and returns relevant time windows.

Official code/demo: https://github.com/line/lighthouse

The project currently has one important limitation for PhotoStar: its documented moment-retrieval models are benchmark-oriented and cap videos at 150 seconds. That makes it a good experiment, not a ready-made VHS-archive solution.

Still, it gives PhotoStar a concrete benchmark question:

> Given a 1–2 minute extracted section, can a text query recover the correct family moment within a few seconds?

**Effort to benchmark:** Low-medium.

## Long-video research — WorldMM

**WorldMM**, a CVPR 2026 Highlight, addresses the much harder problem of reasoning over hours or days of video. It stores complementary episodic, semantic and visual memories instead of reducing an entire video to text summaries. The authors report an average 8.4% gain over previous baselines across five long-video QA benchmarks.

Official project page: https://worldmm.github.io/

Official code is linked from the authors' project page.

This is not something I would put into PhotoStar now. The useful design principle is that **long media needs multiple levels of representation**:

- coarse events for navigation;
- visual embeddings for precise retrieval;
- timestamped frames for evidence;
- transcripts/audio where speech matters.

That maps unusually well onto family home movies.

## Practical architecture

A first data model could stay small:

```text
VideoAsset
  id
  duration
  original_path

VideoMoment
  video_asset_id
  start_ms
  end_ms
  representative_frame
  embedding
  transcript?
  people[]
  event_id?
```

The existing `Asset` abstraction may eventually generalise, but I would not force video through still-image assumptions prematurely. Keep the source video immutable and store analyses/derived frames separately.

## UI — scrub from evidence, not from zero

Opening a two-hour home movie should not drop the user at `00:00:00` with a conventional timeline.

Default to **interesting recovered moments**:

> 00:13:42 — Mum and Dad in garden  
> 00:38:17 — probable Christmas dinner  
> 01:04:51 — Buddy-like black dog / uncertain  
> 01:22:03 — speech mentions "Skegness"

Selecting one opens the video a few seconds before the match, with the exact evidence highlighted.

This is much lower effort for the user than manually scrubbing tapes.

## Photo ↔ movie cross-linking

The most distinctive capability would be reverse-image retrieval across video.

Open a still:

> Dad outside caravan, 1976

Choose:

> **Find this in movies**

PhotoStar searches sampled/key frames and might return:

> `Holiday reel 3 — 18:42`  
> same people, caravan and clothing

Then the still and movie moment can be grouped as the same event while remaining different evidence.

This materially develops Memory Bundles without repeating them: the new capability is **temporal retrieval into long-form video**.

## Current-product signal

Current local photo tools are starting to add video retrieval, but usually as an extension of search rather than family-history evidence. **VISURAL** now searches both photos and videos locally, including visible content, faces, pets, text and speech; its July 2026 release added albums, date navigation and similarity search. **Vistox** similarly indexes photos, video, documents and transcripts on-premise. These products show that multimodal local retrieval is moving from research into practical software.

The gap for PhotoStar is to connect the retrieved moment back to **people, events, still photographs, claims and family stories** rather than merely finding a clip.

## Creative experiment — Still to Motion

Open a photograph and, where real home-movie evidence exists, offer:

> **See the moment move**

Not AI animation.

The UI transitions from the still photograph into the actual matching home-movie footage, beginning a second or two before the closest frame and continuing naturally.

A 1970s still of somebody laughing might dissolve into the real cine footage from the same event.

This gives PhotoStar a much more powerful alternative to synthetic image-to-video animation whenever genuine motion survives.

The provenance distinction is wonderfully clear:

- **Real linked footage** — archival evidence;
- **Interpolated sequence** — derived from real frames;
- **AI animation** — interpretive/generated.

**Effort:** Medium after cross-modal retrieval works. **Creative value:** Very high.

## Best next experiment

Do not build a video player subsystem first.

Take **three representative old home-movie files** and create a throwaway indexing experiment:

1. sample keyframes every 1–2 seconds plus scene-change frames;
2. reuse a still-image embedding model already under consideration for PhotoStar;
3. query with 10 known still photographs from the same events;
4. measure whether the correct movie segment appears in the top 5;
5. separately try Lighthouse on short extracted clips for text-to-moment retrieval.

If still → movie retrieval works at all, it is worth creating `VideoMoment` as a first-class concept.

The larger idea is compelling because it stays true to PhotoStar's archival direction:

> **When real moving footage exists, find it and connect it to the photograph before generating synthetic motion.**
