# PhotoStar2 Daily Inspiration — 10 September 2026 — Viewpoint Graph

## Repository signal

`main` remains at the 26 August documentation commit, but active PR #42 (`task/semantic-relationships-phase1-foundation`) is now the important implementation context. Its current head is `1ab0f573052c9ff66bb9794c70fee7c7b8b9d953`, GitHub reports it mergeable, and the PR deliberately introduces typed semantic entities, propositions, attestations, evidence and decisions before cutting existing gallery/editor/face/group consumers over. `Photograph`/representation semantics are explicitly planned before face identity cutover, while Place/Event and richer locator types remain deferred.

That argues against adding speculative 3D/place schema now. Today's idea should initially live as **derived geometric observations** that can later support semantic propositions once those domains exist.

## Best next idea — Viewpoint Graph

Materially develop the earlier **Memory Spaces / Scene Groups** concept into a concrete geometric layer:

> When several real photographs depict the same room, garden, street or event, estimate where the camera stood and which images geometrically overlap.

Do not start by rendering a pretty 3D scene. Start with a graph:

```text
Photograph A ── strong geometric overlap ── Photograph B
      │                                      │
 relative pose                         relative pose
      │                                      │
Photograph C ── weaker overlap ───────── Photograph D
```

For each candidate scene cluster, PhotoStar could retain observations such as:

- geometric match confidence;
- relative camera pose/orientation;
- overlapping visual regions;
- stable matched points;
- reconstruction confidence/coverage.

Those measurements are not themselves historical facts. They become evidence for propositions such as “these photographs depict the same place/event” only when other context or human review supports that conclusion.

**Likely effort:** medium for a useful prototype; high only if PhotoStar later pursues polished 3D rendering.

**User value:** high. It can connect photographs that differ in crop, people, lighting and decade; strengthen Place Solver and Event Stitcher; reveal nearby views of damaged/obscured details; and provide an intuitive spatial navigation layer without replacing the existing masonry gallery.

## Why this is newly practical

### VGGT — strongest first benchmark

Meta/Oxford's **VGGT (Visual Geometry Grounded Transformer)** won the CVPR 2025 Best Paper Award. From one, a few or hundreds of views it directly predicts camera parameters, depth, point maps and 3D tracks, and its project page provides official code and a Hugging Face demo.

- Official project: https://vgg-t.github.io/
- Official code: https://github.com/facebookresearch/vggt
- Official demo is linked from the project page.

VGGT is attractive for PhotoStar because camera pose and cross-view geometry are useful even if PhotoStar never builds a 3D viewer.

### MASt3R — excellent correspondence/matching reference

NAVER's **MASt3R** is designed around grounding image matching in 3D and includes sparse global alignment, local demos and an official Hugging Face Space for small scenes.

- Official code: https://github.com/naver/mast3r
- The official interactive demo is linked in that repository.

This may prove particularly useful where the primary task is “do these two historical photographs overlap geometrically?” rather than reconstructing an entire scene.

### Fast3R / MUSt3R — larger sets later

Meta's **Fast3R** (CVPR 2025) processes up to roughly 1,500 views together and includes official code plus a Gradio demo that accepts images/video and visualises reconstruction/camera poses.

- Official project/demo: https://fast3r-3d.github.io/
- Official code: https://github.com/facebookresearch/fast3r

NAVER's **MUSt3R** supports multi-view reconstruction and online camera/structure prediction, with official Gradio and visual-odometry demos.

- Official code/demos: https://github.com/naver/must3r

Both are worth Model Lab tests if PhotoStar later tackles large scene clusters. Their model/checkpoint licences require careful review before any eventual distribution; they are suitable research candidates, not automatic production dependencies.

### Classical control — Meshroom/AliceVision

**Meshroom/AliceVision** remains an important non-foundation-model control. It is open source, has precompiled releases, and provides traditional structure-from-motion/multi-view reconstruction with explicit pipelines and 2D/3D inspection. In February 2026 the project added manual matching/alignment tools for archaeological digitisation when automatic matching fails.

- Official project: https://meshroom.org/
- Official code: https://github.com/alicevision/meshroom

A classical baseline matters because old family photographs can contain repeated wallpaper, weak texture and major temporal changes that make learned geometry overconfident.

## Product/software signals

Current family-photo products mostly organise by **time, people, maps and albums** rather than camera viewpoint. Mylio's LifeCalendar combines fuzzy historical dates, events, people and map navigation; Tonfotos combines family relationships, face recognition and maps; MyHeritage Reimagine focuses on rapid album-page scanning plus restoration/enhancement. None of those current public feature sets makes relative viewpoint a core archive navigation primitive.

- Mylio LifeCalendar: https://mylio.com/features/photo-calendar/
- Tonfotos: https://tonfotos.com/
- MyHeritage Reimagine: https://www.myheritage.com/reimagine/

That leaves room for PhotoStar to use geometry as an **archive relationship tool**, not another photogrammetry app.

## Practical UI — Around This Viewpoint

Open one photograph and offer a small optional control:

> **Around this viewpoint — 7 related views**

A simple 2D mini-radar could show camera-direction wedges rather than a full 3D world. Selecting another wedge swaps to the real photograph.

Useful actions:

- **Turn left / right** — move to another genuine viewpoint;
- **Closer / farther** — choose a related view from a different distance;
- **Earlier / later** — if the place is known across dates;
- **Show overlap** — highlight regions visible in both photographs;
- **Use as reference** — expose a clearer real observation to restoration tools.

This leaves the global masonry gallery intact. Spatial navigation appears only inside a scene/place context.

## Strong practical spin-off — Reference Region Finder

Suppose a damaged photograph contains a partly obscured fireplace, sign, ornament or person's clothing. A nearby photograph of the same scene may contain the same physical region clearly.

The Viewpoint Graph can propose:

> **A clearer real view of this area exists in Photo 1842.**

That is valuable even before any reference-assisted restoration is attempted. It gives the user genuine evidence to inspect and can eventually feed PhotoStar's existing preservation-first restoration philosophy.

**Effort after geometric matching exists:** low-medium.

## Strong archive spin-off — Spatial Event Stitching

Yesterday's Event Stitcher used people, clothing, place and date. Add geometry:

> same people + same outfits + compatible date + geometrically consistent room/viewpoints

That provides a much stronger explanation for why disconnected scans probably belong to one event.

Physical sequence still outranks geometry when surviving film strips/roll evidence exists. Geometry is another evidence stream, not a replacement.

## Storytelling/design references

**re.photos** uses rephotography and AI-assisted alignment to compare the same viewpoint across time, while the UK **GhostViewer** launched in March 2026 with landmark-based alignment and live then/now comparison.

- https://www.re.photos/
- https://ghostviewer.co.uk/

**Pastpic** goes further and markets AI “walk into the photo” 3D historic scenes. This is a useful warning as much as an inspiration: PhotoStar should distinguish geometry reconstructed from multiple real views from geometry hallucinated from a single image.

- https://www.pastpic.com/

**HistoSplat** uses hundreds of photographs and Gaussian splatting to make high-density 3D records of historic monuments. It shows how compelling real multi-view reconstruction can be when sufficient source coverage exists.

- https://histosplat.com/

The original **3D Gaussian Splatting** authors provide official code and desktop viewers, but no simple author-hosted “upload your family photos” web demo was found.

- Official code: https://github.com/graphdeco-inria/gaussian-splatting

## Creative concept — Room Through Time

For a family home photographed repeatedly across decades, register only the geometry that is genuinely supported across photographs:

```text
1954 ── 1963 ── 1978 ── 1996 ── 2026
```

A user could stand on a reconstructed camera point and move between the **actual photographs taken from nearby viewpoints** at different dates.

Changes become visible:

- door added;
- fireplace replaced;
- wallpaper changes;
- tree grows;
- extension appears;
- furniture moves.

Crucial rule: unknown space remains unknown. If no photograph shows behind the camera, PhotoStar should not invent it merely to make a seamless virtual room.

This is materially different from `Stand Here`: that concept aligned one historical viewpoint with the modern world; **Room Through Time** connects a network of genuine historical viewpoints and their changes.

## More experimental — Evidence Splat

Only once a scene has enough overlapping real photographs, PhotoStar could optionally create a Gaussian-splat/3D representation as a clearly labelled **derived visualisation**.

Every rendered region should retain source coverage metadata:

- strongly observed by several photographs;
- weakly observed;
- interpolated between observations;
- no evidence.

That would make the 3D view an inspectable map of photographic evidence instead of a visually convincing but provenance-free synthetic scene.

## Best next experiment

Do not build a 3D UI.

Take roughly **10 known scene groups**, ideally 5–30 photographs each:

- one room photographed repeatedly;
- garden/house exterior;
- wedding or party with many viewpoints;
- street/place across several dates;
- at least two deliberately difficult groups with few shared features.

Benchmark:

1. VGGT;
2. MASt3R;
3. optionally Meshroom/AliceVision as a classical control.

For each pair/group measure only:

- did it correctly detect usable overlap?;
- are estimated camera relationships plausible?;
- does the geometry help rank same-scene photographs?;
- are failures visibly low-confidence, or confidently wrong?

Then build one tiny prototype: **Around This Viewpoint** using real photographs only.

If that works, Viewpoint Graph becomes today's best next idea to explore. It develops Memory Spaces into something concrete, improves several existing PhotoStar concepts at once, and fits PR #42's evidence architecture cleanly by keeping model geometry as observations rather than prematurely promoting it to truth.
