## Best next idea — Photo Lineage

PhotoStar should learn the difference between:

- the same file;
- the same digital image after resize/recompression;
- a crop or edit derived from another image;
- two scans of the same physical print;
- two prints made from the same photographic exposure;
- merely similar photographs of the same scene.

Those are not the same relationship.

A family archive commonly contains something like:

`physical print -> 2004 flatbed scan -> cropped JPEG -> emailed copy -> 2026 rescan -> restored version -> colourised version`

Today those may appear as six unrelated images or as an over-aggressive duplicate group. PhotoStar should instead show one historical photograph with an explainable **lineage of representations**.

**Value: very high. Effort: low-medium for a useful first version; medium for robust crop/rephoto matching.**

## Why this matters specifically to PhotoStar

PR #42 is already moving toward Photograph/Representation semantics. Photo Lineage gives that abstraction a concrete product job.

If three files are recognised as representations of the same photograph, PhotoStar can avoid:

- analysing the same face six times;
- counting the same image repeatedly in archive statistics;
- asking the same identity/date question repeatedly;
- treating restoration-generated detail as independent historical evidence;
- cluttering Story Rivers, Story Cuts and search results with copies.

But it should **not delete or silently hide the source files**. Different representations may preserve different evidence: a newer scan may have more detail; an old crop may preserve a lost annotation; a restoration is useful for viewing but weaker as source evidence.

## UI — one photograph, its versions underneath

Normal browsing shows the preferred representation once.

Open it and expose a small control:

**Versions (6)**

Then:

- Original/source scan
- Later rescan — higher resolution
- Crop — derived from 2004 scan
- Restoration — generated 2026
- Colourisation — generated 2026
- Emailed copy — lower quality

For every edge, **Why linked?** should expose the evidence:

> Same underlying image — confirmed  
> Strong local-feature match despite crop  
> File imported from restoration output  
> Human confirmed same physical print

This is much better than a generic “duplicates” drawer.

## Practical v1 — a fingerprint ladder

Don't start with a new neural model. Use progressively more expensive evidence:

1. **Cryptographic hash** — byte-identical file.
2. **Metadata/known derivation** — PhotoStar itself created the crop/restoration/export.
3. **Perceptual hash** — resized/recompressed/lightly changed copy.
4. **Crop-resistant/local-feature verification** — crop, rotation, perspective or rephotographed print.
5. **Embedding retrieval** — candidate generation only.
6. **Human confirmation** where identity is consequential or ambiguous.

This distinction is important: semantic embeddings are excellent at finding *similar* photographs and therefore dangerous as proof that two files are the same photograph.

Current software already covers pieces of this. PhotoPrism stacks files believed to have the same origin and explicitly includes originals, edited versions and compressed versions; exact duplicates use SHA1. digiKam builds image fingerprints for duplicate/similarity retrieval. Tropy takes the object-oriented approach of allowing multiple photos to form one item, though for document pages rather than derivative image provenance.

Sources:
- https://docs.photoprism.app/user-guide/organize/stacks/
- https://docs.photoprism.app/user-guide/library/duplicates/
- https://docs.digikam.org/en/left_sidebar/similarity_view.html
- https://docs.tropy.org/in-the-project-view/combine_photos

PhotoStar's synthesis should be stronger: **same historical photograph + explicit derivation/source relationships + retained evidence**.

## Research Lab — AnyPattern / image-copy detection

**AnyPattern: Towards In-context Image Copy Detection** explores copy detection under new manipulation patterns without retraining. Its project page provides the paper, dataset and author-linked code resources:

- Official project page: https://anypattern.github.io/

This is an author project with code/data links, not a third-party reproduction. There is no useful PhotoStar-style hosted upload demo on the project page, so the code/dataset are the practical research resources.

I would not adopt the model first. I would use its manipulation taxonomy to build a PhotoStar benchmark containing the transformations we actually care about:

**crop, rescan, perspective, faded scan, contrast change, restoration, colourisation, JPEG recompression and phone photograph of a print.**

## Research Lab — BINDER as a useful protocol, not a domain model

Harvard Medical School's Image Data Analysis Core created **BINDER**, a same-source near-duplicate benchmark with transformations including rotation, translation, scale, perspective, contrast and compression. The authors provide the dataset, project page and official GitHub repository:

- Official project: https://hms-idac.github.io/BINDER/
- Official code: https://github.com/HMS-IDAC/BINDER

There is no useful interactive demo; the value for PhotoStar is the evaluation protocol. Its biomedical images are the wrong domain, but its distinction between **same-source transformed image** and merely similar content is exactly the distinction PhotoStar needs to measure.

## Provenance standard worth watching — C2PA

The Content Authenticity Initiative now maintains production JavaScript, Rust, Python and other SDKs for reading, validating and creating C2PA provenance manifests. The current JavaScript repository supports both browser and Node use and was consolidated into the new `contentauth/c2pa-js` repository in June 2026.

- Official CAI repositories: https://github.com/contentauth/
- Official current JS SDK: https://github.com/contentauth/c2pa-js
- Official Rust SDK: https://github.com/contentauth/c2pa-rs

This is not needed to identify old family scans: historical JPEGs generally won't contain a trustworthy signed provenance chain. But PhotoStar **could record provenance for new derivatives it creates**. A future exported restoration could carry machine-readable evidence that it derives from a particular source representation.

Treat that as interoperability, not as PhotoStar's internal data model.

## Practical improvement — Best source, best view

Once representations are grouped, distinguish two choices:

**Best evidence source** — least altered / highest-fidelity surviving source.

**Best viewing representation** — perhaps cleaned, restored or colour-corrected.

Those need not be the same file.

That would materially strengthen Trust Lens and restoration. PhotoStar could happily show the restored version in a Story Cut while the evidence panel points back to the untouched scan.

## Large-library UX — collapse copies without losing them

A collection of 40,000 files might represent substantially fewer unique photographs.

Gallery/search should default to **Photographs**, not raw files, with an optional:

> 31,842 photographs · 39,106 representations

That makes collection size meaningful and reduces clutter without destructive deduplication.

A `Show all representations` switch remains available for archive-management work.

## Important hard case — same exposure, different print

Two scans can depict exactly the same photographic exposure while coming from **different physical prints**.

That distinction can matter if one print has:

- writing on the back;
- a studio stamp;
- different crop/border;
- album mounting traces;
- damage or retouching;
- different provenance through the family.

MoMA has noted a closely related computer-vision failure mode: matching systems can confuse a photographed work with a different print/edition of the same image. That is a useful warning for family archives too.

Source: https://www.moma.org/calendar/exhibitions/history/identifying-art

So don't collapse the physical layer. A sensible future hierarchy is:

`Exposure / image event -> Physical print(s) -> Digital representation(s)`

PhotoStar does not need all three levels exposed in normal UI, but the model should avoid making them impossible.

## Creative concept — The Life of a Photograph

Usually PhotoStar tells the story *inside* a photograph.

Occasionally tell the story **of the photograph itself**:

> 1958 — photograph taken  
> 1960s — print placed in Album 2  
> 1989 — Margaret writes “Cromer” on the back  
> 2004 — first flatbed scan  
> 2012 — emailed to Robin  
> 2026 — rescanned and restored

Only show events for which evidence exists.

This connects Album Grammar, The Other Side and restoration provenance into something surprisingly human: family photographs themselves have biographies.

## Experimental concept — Copy migration map

Across a large inherited archive, PhotoStar might discover that particular scans recur in several imported folders or relatives' collections.

Instead of calling them duplicates, show a source map:

`Mum's CD -> Robin's Pictures -> family USB -> restored collection`

This can help identify which source likely contains the best surviving copy and reveal where a photograph travelled digitally.

Do **not** infer who sent what to whom unless metadata or testimony establishes it. File occurrence is evidence of presence, not transfer history.

## Best next experiment

Build a deliberately nasty **200-group PhotoStar lineage benchmark** from known source photographs. For each source create or collect:

- byte copy;
- JPEG recompression;
- resize;
- crop;
- rotation;
- contrast/fade variation;
- phone rephotograph;
- restoration;
- colourisation;
- genuinely different near-neighbour from the same sequence.

Compare SHA, pHash, crop-resistant hashing/local features and existing PhotoStar embeddings.

The critical metrics are not just recall. Measure separately:

1. **same file/derivative recall**;
2. **same physical print recall**;
3. **false merges of two genuinely different photographs**.

Optimise the third aggressively. A missed link is irritating; collapsing two distinct historical photographs is data corruption at the semantic level.

## Recommendation

**Photo Lineage is today's best next idea.**

It gives the emerging Photograph/Representation architecture an immediate user-facing purpose, reduces duplicated analysis and navigation clutter, improves restoration trust, and connects Album Grammar and The Other Side without repeating either feature.

The design rule should be:

> **Deduplicate computation and presentation, not history. Preserve every source and make the relationship between versions explicit.**
