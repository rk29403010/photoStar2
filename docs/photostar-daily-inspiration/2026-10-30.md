## ★ Best next idea — Verso Link / Flip the Print

A physical photographic print is one historical object with at least two sides. A back may contain names, a studio stamp, a processing date, handwritten notes, or nothing at all. Existing digital front/back scans often become two unrelated gallery assets. Treat them as two *views of the same physical artefact*, while keeping the original files and checksums.

**Proposed single-photo UI:** a subtle `↻ Back` control; front displayed by default, reverse on flip. Beneath the back: transcription, evidence status, writer (if known), date-role classification, and links to claims on the front. In the gallery, backs should not create extra photo thumbnails or inflate image counts; a small back-side badge reveals their presence. A `Reverse sides to review` filter prioritises pairs with text, mismatched filenames or uncertain matches.

Example:
- Front: beach photograph, estimated 1958–1968.
- Back: handwritten `Margaret & Joan, Yarmouth` (possible identification); printed lab stamp `MAR 1971` (print processed by then, *not* evidence photo was exposed in March 1971); handwritten `Summer 1962` (possible event date, author unknown).
- A user can confirm the transcription and the physical front/back link without automatically confirming names, date or location. The reverse scan is a source for those later claims.

**Data model:** `physical_print` identity; `print_side` records with `role=front|back|unknown`, linked immutable asset IDs and file hashes; `pair_decision` with `machine_suggested|human_confirmed|rejected` and reversible history. Evidence claims retain side/region/source, author attribution, and temporal role `exposure|printing|inscription|unknown`. No date propagation without a separately reviewed claim. Multiple prints of the same exposure may each have different inscriptions.

**Suggested minimum workflow:** batch-select fronts/backs or use a filename suffix rule (`_b`, `_back`, `verso`), show a two-column pairing review with manual drag-to-relink and an unmatched queue, then display `Flip` in the existing photo viewer. Deterministic pair proposals only for first version. Never pair by alphabetical adjacency alone; a scanned batch may have missing prints or changed orientation.

**User value:** high for inherited printed collections; reduces orphan files and prevents historically important annotations being lost. **Initial effort:** 4–7 focused development days for pair model, manual review and viewer; another 3–5 days for searchable reverse transcription and date-role chips. Estimates assume existing asset and evidence infrastructure can be reused.

## Research/model lab — official resources and demonstrations

**1. TrOCR (Li et al., AAAI 2023)** — transformer-based handwritten text recognition. Paper: https://arxiv.org/abs/2109.10282 ; **official Microsoft author code:** https://github.com/microsoft/unilm/tree/master/trocr ; **official Microsoft model/checkpoint with runnable example:** https://huggingface.co/microsoft/trocr-base-handwritten . The model is designed for cropped *single text lines*, not an entire photo back with multiple regions; line detection is needed first. The Microsoft model card currently notes that the older `transformers` pipeline approach is incompatible with Transformers v5. No verified first-party hosted interactive upload demo; many Hugging Face Spaces are third-party.

**2. docTR** — text detection plus recognition (suitable for printed studio stamps, handwriting as an unproven extension). **Official source:** https://github.com/mindee/doctr ; **project-hosted browser demo:** https://demo-doctr-tensorflowjs.mindee.com/ ; local Streamlit demo supplied in repository. Project currently maintained by t2k GmbH. Demo page reachable, not benchmarked on reverse scans. Apache-2.0 library; packaging a Python runtime on Windows would be extra work.

**3. Kraken** — trainable historical handwritten text recognition, useful if TrOCR fails on cursive writing. **Official author code:** https://github.com/mittagessen/kraken ; **official documentation/runnable CLI:** https://kraken.re/ . No verified first-party public upload-and-run demo. The repository currently describes Linux/macOS installation; Windows would need packaging/compatibility investigation. Requires selecting a suitable model; not a zero-setup recognition system. Apache-2.0.

**4. Transkribus** — a useful external accuracy comparator, not a proposed automatic cloud dependency. **Official live upload demo:** https://www.transkribus.org/ai-text-recognition ; **official API documentation:** https://docs.transkribus.org/processing/text-recognition . Commercial hosted service, so only use non-sensitive benchmark samples with permission; the API requires an eligible plan. Its handwriting models should not be assumed to recognise faded 1960s pencil notes reliably without testing.

**Recommendation:** do *not* integrate a model initially. First import front/back pairs and support manual transcription. Then compare existing PhotoStar vision text output, TrOCR on cropped lines, docTR for stamps and optionally Kraken on 40 varied back scans.

## Art and experimental storytelling — The Note Behind the Moment

Susan Hiller's *Dedicated to the Unknown Artists* (1972–76) assembled hundreds of anonymous seaside postcards with maps and classification charts, showing how text, labels and collections transform the meaning of ordinary photographs. Institutional reference: https://artcollection.dcms.gov.uk/artwork/19096/ ; British Museum collection discussion: https://www.britishmuseum.org/collection/object/P_2018-7009-169-1-12 . This is an artistic precedent, not a ready-made product interaction.

**Experimental concept: The Annotation That Arrived Later.** The user flips a family print, sees a dated inscription and can compare *when the image was made* with *when it was annotated*. A 1950 photograph labelled in 1980 can become a short two-time-layer story: the moment photographed and the later person remembering it. A gallery `Notes added decades later` lens could surface these especially evocative artefacts. Never invent the writer or date; unknowns remain visible. Future optional extension: a small interactive exhibition with front/back flips and linked original audio memories.

## Small benchmark and go/no-go

Use 60 real prints: 20 front/back pairs with clear filenames, 20 out-of-order or missing backs, 20 handwritten backs with uncertain names/dates/stamps. Test pairing precision (false confident matches must be zero), time per manual correction, ability to preserve hashes and source sides, text retrieval, distinction between exposure/print/annotation dates, and whether users can navigate to the original back in one click. For handwriting, measure character error rate and wrong-person/date assertions; compare local inference time and peak RAM on a typical Windows machine.

**Best next build:** `physical_print` + `print_side` linkage and read-only `Flip` UI, with a manual pairing queue. This provides immediate value with no new model, then enables reverse-side OCR, provenance-aware date investigation and more ambitious storytelling. Do not prioritize new dependencies ahead of the recorded security backlog.
