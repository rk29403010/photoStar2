# Tagging Vocabulary And Review Design

**Date:** 2026-04-03

## Goal

Replace the current free-form gallery tags with a controlled tagging system that:

- keeps one canonical vocabulary across AI, system, and manual tagging
- prevents AI from silently creating arbitrary new tags
- supports deterministic date tags and other code-generated tags
- supports manual tagging from both the single-photo view and bulk gallery selection
- uses a generic review queue that can later handle groups, sensitivity, and other reviewable work
- migrates existing tags into the new model without throwing away useful historical assignments

## Why

The current tags are not stable enough to browse or filter confidently:

- some are far too broad to be useful, such as `adult`
- some are too narrow or one-off
- inflected or stylistic variants fragment the vocabulary
- AI can drift into new terms while ignoring near-equivalent existing ones

The app needs tagging to behave more like a maintained catalog than a stream of uncurated labels.

## Product Principles

- There is one shared canonical tag vocabulary.
- Tag assignments preserve source metadata.
- AI chooses from approved tags and proposes new ones for review instead of creating them directly.
- Deterministic tags, especially date tags, should be generated locally and reproducibly.
- Manual edits represent explicit user intent and should be easy to apply in single-photo and bulk workflows.
- Review infrastructure should be generic so it can later support tags, groups, sensitivity, and similar moderation flows.

## Core Model

### Canonical Tags

Add a canonical tag definition layer that stores the approved vocabulary.

Each canonical tag should support:

- stable id
- canonical label
- optional description
- status such as `active` or `retired`
- optional category for future grouping
- created/updated timestamps

### Tag Aliases

Add an alias layer that maps legacy spellings, inflections, and synonyms onto canonical tags.

Examples:

- `affectionate` -> `affection`
- `summer time` -> `summer`
- `1930's` -> `1930s`

Filtering and search should resolve aliases to the canonical tag.

### Asset Tag Assignments

Store asset-tag links separately from tag definitions.

Each assignment should include:

- asset id
- canonical tag id
- source kind: `manual`, `system`, `ai`, or `legacy_ai`
- source record id where relevant
- optional confidence for AI-generated assignments
- created/updated timestamps

This keeps one shared vocabulary while preserving where each assignment came from.

## Review System

Do not build a tag-only review queue.

Instead, add a generic review-item system that can support:

- tag proposals
- future group review
- future sensitivity review

Each review item should include:

- stable id
- review item type such as `tag_proposal`
- subject type and subject id
- payload JSON for type-specific details
- status such as `pending`, `approved`, `rejected`, `dismissed`, `superseded`
- optional reviewer id and review note
- created/updated/reviewed timestamps

For tags, the review queue should back both:

- a central inbox view
- per-photo contextual suggestions

The queue is the same underlying system viewed through different filters.

## Tag Sources

### AI Tags

AI should assign only approved canonical tags directly.

If AI believes a needed tag does not exist, it should create a `tag_proposal` review item rather than silently assigning a new free-form tag.

The AI prompt should receive:

- the approved vocabulary
- alias guidance
- instructions to prefer existing tags whenever possible
- explicit rules against overly broad or trivial tags

### System Tags

System tags are deterministic tags generated by code.

The first important system family should be date tags derived from the resolved photo date:

- centuries, for example `20th century`
- decades, for example `1930s`
- period buckets, for example `early 1930s`
- year tags, for example `1932`
- seasons, for example `summer`

System tags should use the same canonical tag model and assignment table as AI and manual tags, but with `system` as the source kind.

### Manual Tags

Manual tagging should allow the user to:

- apply approved tags
- remove existing assignments
- create a new canonical tag intentionally

Manual tagging must be available in:

- the single-photo experience
- bulk gallery selection workflows

Manual tag creation is an explicit human action, not a review proposal.

## Initial Vocabulary

The app should ship with an initial approved vocabulary before AI is asked to behave better.

### Seeded Date Vocabulary

Seed deterministic date tags so the system has an immediately useful backbone:

- centuries: `19th century`, `20th century`, `21st century`
- decade tags
- early/mid/late decade tags
- year tags where date precision supports them
- seasons

### Seeded Starter Vocabulary

Also seed a small hand-authored starter vocabulary for common human-meaningful themes.

Examples:

- people/context: `portrait`, `group photo`, `family`, `childhood`, `everyday life`
- mood/interaction: `affection`, `celebration`, `play`, `ceremony`
- setting/activity: `indoors`, `outdoors`, `travel`, `holiday`, `meal`, `sport`
- visual/document type: `document`, `snapshot`, `formal portrait`

Avoid broad low-value tags such as:

- `adult`
- `person`
- `photo`

Avoid a large taxonomy in v1. The initial set should be curated, useful, and easy to maintain.

## Migration Strategy

The migration should bootstrap a working set rather than merely preserving the current mess.

### Inventory

Start by inventorying the existing tags with:

- label
- usage count
- example assets
- first-seen/last-seen timestamps if available

### Normalize

Apply high-confidence normalization only:

- case
- whitespace
- punctuation
- known alias mappings
- obviously equivalent date forms

Do not silently merge semantically distinct tags just because they look similar.

### Canonicalization

Build the initial canonical vocabulary from:

- seeded date tags
- seeded starter vocabulary
- promoted high-signal legacy tags that are clearly useful

### Backfill

Convert current tag assignments into the new model by:

- mapping confident legacy tags to canonical ids
- storing the resulting assignment as `legacy_ai` or another legacy source kind
- creating review items for unmapped or ambiguous legacy tags

### Stabilize Future AI Tagging

After the canonical vocabulary exists, future AI tagging should run only against the approved set plus proposal generation. This prevents the corpus from immediately drifting again.

## User Experience

### Gallery

- keep a tag filter in the library toolbar
- show canonical tags rather than raw free-form labels
- later allow source-aware filtering if needed, but not in v1

### Single Photo

- show assigned tags with source badges
- allow add/remove manual tag actions
- show AI suggestions in context
- allow approving/rejecting tag proposals from the photo view

### Bulk Gallery Selection

- add/remove approved tags for multiple selected assets
- avoid requiring the user to tag one photo at a time

### Review Inbox

- central queue filtered by review item type
- start with tag proposals
- design the model so future review types can use the same surface

### Vocabulary Management

Provide a management surface for:

- rename
- merge
- alias management
- usage inspection
- retirement of low-value tags

## Precedence And Semantics

- Canonical tag definitions own the vocabulary.
- Alias resolution maps inputs to canonical tags.
- Manual assignments are explicit and should not be overwritten by AI cleanup.
- System-generated date tags should be re-generatable and deterministic.
- AI proposals should stay pending until approved or rejected.

## Performance Notes

Tag filtering should not rely on repeatedly parsing AI JSON forever.

Use explicit relational tag tables for:

- definitions
- aliases
- assignments

This gives stable filtering, counts, and review workflows, and avoids coupling the tag UX to raw AI payload shape.

## Out Of Scope For This Slice

- deep hierarchical taxonomy management
- collaborative permissions
- advanced machine-learning feedback loops for tag quality
- automatic semantic merging of ambiguous terms

## Recommended First Slice

1. Add canonical tag, alias, assignment, and review-item tables.
2. Seed the initial date and starter vocabularies.
3. Build the migration pipeline for existing tags.
4. Add deterministic date-tag generation.
5. Add manual tagging for single-photo and bulk gallery selection.
6. Add tag proposal review in context and in the central inbox.
7. Update AI tagging to consume the approved vocabulary and emit proposals for missing concepts.

This sequence yields a usable tagging system quickly while leaving room for future review types such as groups and sensitivity.
